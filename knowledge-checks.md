# Knowledge Checks and Self-Critique

These are representative checks for the highest-value topic families in the roadmap, not a test suite for every leaf topic. For each row, answer aloud first, then verify against the expected-answer notes. Add fresh questions from real job descriptions and mock feedback. Do not memorize answer text; demonstrate the reasoning.

## Four-Level Check Set

## Answer Key: Minimum Correctness

- **Coding:** Hash-map lookup is expected O(1), with caveats around hashing/collisions and resizing. Pair-sum typically scans once with a complement map; clarify whether the same element can be used twice. LRU combines a hash map and doubly linked list; capacity zero behavior must be explicit.
- **Go:** A nil interface has no dynamic type/value; a typed-nil pointer stored in an interface has a dynamic type and is not itself nil. Cancellation must reach every blocking send/receive; bound workers and close output only after all senders finish. Use `go test -race` for data races, not as proof of all concurrency correctness.
- **PostgreSQL:** MVCC gives statements a snapshot consistent with its isolation semantics; it does not eliminate write conflicts or all locks. Inspect `EXPLAIN (ANALYZE, BUFFERS)`, estimates vs actuals, I/O, indexes, lock waits, and connection pressure. Use expand/migrate/contract patterns and rollback-safe backfills.
- **Kafka:** Ordering is per partition. Committing before an external effect can lose work; effect-before-commit can duplicate work. Use idempotency or a transactional sink boundary; explain what Kafka's transaction does and does not cover.
- **Distributed systems:** During partitions, linearizable write availability cannot be guaranteed for every partitioned client. Use stable idempotency keys and durable result lookup for retry. Outbox commits business state and event intent together, then relays at least once; consumer deduplicates.
- **System design:** Requirements, SLOs, scale, and invariants precede product selection. A capacity estimate should be dimensionally coherent and include peak, storage growth, retention, and headroom. Evaluate security, operations, migration, and failure recovery as first-class constraints.
- **Cloud/platform:** Kubernetes reconciles declared desired state and offers primitives, but not every app-level service. Readiness controls traffic eligibility; liveness restarts stuck processes and can worsen overload if misused; startup probes protect slow startup. Platform success includes adoption and developer outcomes.
- **Security:** A normal signed JWT is integrity-protected, not confidential by default. Validate algorithm/signature, issuer, audience, expiry/not-before, and key rotation. Enforce object authorization server-side and tenant-scoped in queries, not only in UI or token claims.
- **SRE/observability:** Traces connect work across services; metrics support aggregate alerting; logs explain specific events. p99 can worsen with a small pathological tail. SLO alerts should be actionable and tied to user impact; do not alert on every metric fluctuation.
- **AI:** RAG provides external/retrieved context at inference; fine-tuning changes model behavior/weights. Treat retrieved text and tool outputs as untrusted; enforce permissions outside the model. Evaluate retrieval, generation, safety, latency, and cost separately.
- **Staff:** Staff impact is demonstrated through scope, direction, influence, adoption, risk reduction, and multiplying team capability, not title or meeting count. Influence starts by understanding incentives and constraints, documenting options, and getting an explicit decision owner.

## Second-Pass Self-Critique

Ask the following as though an interview were tomorrow. A “no” is a practice task, not a permanent judgment.

| Possible failure gap | Why it is plausible for this profile | Cheap diagnostic | Repair priority |
| --- | --- | --- | --- |
| Coding speed and fluency under a blank editor | Senior production experience does not guarantee interview-style timed DS&A fluency | Two 40-minute medium problems in Go with tests and verbal explanation | Critical until stable |
| Project-depth interrogation | The role history includes complex systems; interviewers can probe every decision and personal contribution | Give a 10-minute architecture walkthrough, then answer 15 “why/what failed/how measured” follow-ups | Critical |
| Senior vs Staff scope evidence | Years in role do not by themselves prove cross-team direction or durable leverage | Map three stories to teams affected, decision authority, adoption, and measurable outcomes | High for Staff/Lead |
| Distributed-systems guarantees | Terms such as idempotency, exactly once, consistency, and quorum are easy to overstate | Explain one DB/Kafka failure sequence and mark every atomicity boundary | Critical |
| Database diagnosis depth | ORM familiarity can mask gaps in query plans, isolation, vacuum, and locking | Explain a real or lab `EXPLAIN` plan and a deadlock/serialization failure | High |
| Go concurrency lifecycle | Goroutine leaks and cancellation bugs often survive happy-path tests | Build a pipeline with early consumer exit; prove all goroutines stop | High |
| Platform product thinking | Infrastructure fluency can be described as tools rather than user and adoption outcomes | Pitch one paved road with developer journey, policy, SLO, adoption metric | High for platform roles |
| Security and tenant boundaries | Identity experience can leave gaps in object authorization, data filtering, and workload identity | Threat-model cross-tenant object access and token validation | High |
| AI quality and security | AI literacy is rising, but a demo can hide weak evaluation or unsafe tools | Design an eval set and prompt-injection/tool authorization test | Medium generally; high for AI roles |
| Behavioral story quality | A long career contains experience but not necessarily concise, measurable narratives | Record 6 STAR-L answers; check personal actions, outcome, learning, and defensible metrics | Critical |
| Cloud provider specificity | Broad AWS/Azure exposure may not match a target team's deep provider expectations | Select one target posting and explain its network, IAM, compute, data, and failure model | Role-dependent |
| Compensation/company data accuracy | No target geography or level was supplied | Define country/city, level, currency, equity basis, and role family before comparing offers | Blocked until specified |

## Repeatable Audit Loop

After each mock or interview: (1) capture the exact question and what was evaluated; (2) rate evidence, not confidence; (3) identify one root cause; (4) add or revise a roadmap node only if the gap recurs or maps to role evidence; (5) schedule a practice; (6) retest with a different prompt. Continue until no **critical** gap repeats across three mocks. This defines practical saturation for one candidate and role set; it does not claim that no other interview topic exists.
